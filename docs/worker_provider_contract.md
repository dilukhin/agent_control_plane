# R4: контракт исполнителя и поставщика 1.0

Реализация: `internal/execution`; приём заявления исполнителя —
`core.Transaction.RecordWorkerReport`. Задача: [№11](https://github.com/dilukhin/agent_control_plane/issues/11).
Это местный библиотечный контракт. Транспорт, служба, реальная модель,
планировщик, распределённые полномочия и выбор поставщика не реализуются R4.

## Границы

Контроллер владеет `Store`, проверенной политикой и каноническим описанием
операции. `Worker` получает копию ограниченного задания и функцию проверки
полномочий/регистрации сигнала активности. `Provider` получает только модель,
минимизированный вход и лимиты. Ни одному из них не передаётся `Store`, функция
подтверждения результата или возможность изменить политику.

`Capabilities` описывает доступность. `ExactPolicy` независимо проверяет
точное совпадение версии политики, исполнителя, поставщика, модели, действия,
цели, класса воздействия и класса данных, разрешение внешней передачи,
срок действия и лимиты. Отсутствие разрешения означает отказ. Подстановок,
масок и наследования прав от текста задания нет. Снимок разрешений копируется
при создании; изменяемая реализация `Policy` должна быть безопасна при
одновременных вызовах. Политика проверяется до принятия, непосредственно перед
запуском, при сигнале активности и перед приёмом результата.

Идентичность исполнителя и признаки поставщика берутся из доверенной местной
композиции адаптеров. Это не аутентификация удалённого участника: будущий
транспорт обязан установить её до вызова этого интерфейса. Самозаявленные
поля удалённого клиента не должны превращаться в доверенные `Capabilities`,
`Grant` или `Job`.

Эталонный `Local` поддерживает только `analyze/read_only`: нет запуска команд,
записи файлов, вызова инструментов или сетевого клиента. `EchoProvider` и
`DigestProvider` — два детерминированных тестовых поставщика без оплаты;
замена требует другого экземпляра адаптера и явно разрешённых provider/model,
но не изменения логики `Runner`. Бюджет `Units` здесь считает байты входа;
он не означает денежный лимит или число оплаченных токенов реальной модели.

## Жизненный цикл

1. Вызывающая доверенная сторона создаёт Task/Operation и переводит её в ready
   через существующий R2/R3 API. Описание операции неизменно.
2. `Execute` проверяет версию 1.0, ID, время и бюджет. `Accept` — чистая местная
   проверка без внешнего действия; явный отказ не создаёт попытку и сохраняет
   ограниченную запись решения. Повтор отклонённого предложения не становится
   новым разрешением: после изменения условий нужен новый message ID.
3. Принятие предложения, его дедупликация, создание Attempt и запись решения
   фиксируются одной транзакцией `ProcessMessage`. После ошибки фиксации
   исполнитель не запускается. Нельзя предполагать, что транзакция откатилась:
   сначала требуется чтение состояния.
4. Внешний вызов происходит только после подтверждённого commit, вне
   транзакции. Один `Execute` вызывает одного исполнителя один раз. Повтор того
   же сообщения лишь подтверждает ранее записанное состояние. Новый message ID
   не обходит проверку revision/state/attempt. Конкурирующий запуск отсеивает CAS.
5. Сигнал активности — существующее `operation.progress`, а не новая машина
   состояний. Проверяются текущие attempt/lease/generation/owner, политика и
   крайний срок. Сигнал сохраняется как заявление исполнителя, не продлевает
   полномочия и не подтверждает результат. На попытку допускается не более
   32 сигналов, включая проверки контроллера и местного исполнителя.
6. Результат становится `worker_report`; атомарно с записью и дедупликацией
   выполняется только executing → verifying. Нет перехода к succeeded.
   Разные данные под одним ID результата дают collision. Подлинный поздний
   отчёт от ранее назначенного, уже отозванного владельца сохраняется как
   evidence без изменения состояния. Подмена источника, цели, поколения,
   lease или типа evidence отклоняется; истёкший срок не даёт принять активный
   результат. Проверка срока внутри транзакции использует часы контроллера.
7. Timeout, отмена, ошибка, panic, превышение бюджета или отзыв прав после
   выдачи попытки приводят к unknown_outcome и отзыву её полномочий через R3.
   Ошибка адаптера заменяется фиксированным кодом; её исходный текст не
   сохраняется. Отдельная запись восстановления ограничена двумя секундами и
   выполняется даже после отмены вызывающего контекста. Ошибка этой записи
   возвращается вызывающей стороне: никаких скрытых повторов.
8. Проверку фактического состояния делает доверенный проверяющий компонент
   по `VerificationPolicyRef` через существующие R3 API. Только доказанная
   безопасность повтора возвращает ready. Новая попытка требует новых ID и
   ссылки на предыдущую попытку текущего поколения. Для изменения внешней цели
   остаются обязательны доказанная остановка старого исполнения либо защита
   самой цели от устаревшего поколения/повтора.

## Ограничение времени и отмена

Верхняя граница — 5 минут, 64 KiB входа/выхода и 65536 тестовых единиц работы.
Разрешение и запрос могут только уменьшать эти пределы. Абсолютный `Deadline`
не должен выходить за срок разрешения и заявленную длительность. Контекст
вызывающего кода может сократить ожидание ещё сильнее. Функции `Accept`,
`Capabilities` и `Policy.Check` обязаны быть быстрыми местными проверками.

`Run` получает контекст отмены. Контроллер прекращает ожидание независимо от
ответа поставщика, но Go-код внутри процесса нельзя принудительно остановить
этим контрактом. Непослушный адаптер может продолжить работу и удержать одну
горутину; поздний возврат сам не меняет состояние и не создаёт повторный вызов.
В тесте такой адаптер явно освобождается. Встроенные поставщики ограничены
размером входа и исполняют конечные вычисления. Для произвольного кода, реальных
моделей и внешних изменений необходимы отдельная изоляция процесса,
ограничение числа активных вызовов и защита целевого объекта. R4 не является
песочницей для недоверенного кода и не обещает глобальное однократное исполнение.

## Сохранность, восстановление и совместимость

Control protocol остаётся 1.0, схема SQLite — v3. Новых таблиц, миграций,
зависимостей и обязательных полей старых записей нет. Версия контракта R4
проверяется отдельно; несовместимый запрос отвергается. Используются существующие
operation.offer/progress/result_reported и виды evidence. История подчиняется
[правилам R3.3](retention.md); автоматическая очистка здесь не запускается.

Сохраняются попытка, владелец, поколение, решение о принятии, сигналы активности,
заявление результата, отзыв и хеш предложения. Текст входа/выхода не сохраняется.
Оперативный контекст, замыкание политики и крайний срок не восстанавливаются
для продолжения исполнения. После перезапуска `InspectRecovery` классифицирует
executing/verifying; контроллер устанавливает принадлежность попытки и
проверяет/отзывает её через `InvalidateAttempt`. Автоматического возобновления
или повторного вызова нет. Повторное открытие БД не отзывает чужие попытки.

Потеря процесса между сохранением попытки и вызовом поставщика остаётся
неизвестным результатом: локального факта «вызов ещё не был сделан» после
перезапуска недостаточно. Хеш сообщения/результата — средство идентичности,
не доказательство истинности и не способ восстановить сам артефакт. Если
артефакт нужен после перезапуска, его сохранение в разрешённом хранилище должен
обеспечить будущий доменный адаптер до выдачи проверяемой ссылки.

## Данные и дальнейшая интеграция

Вход обязан быть минимизирован и не содержать секретов. Контракт не способен
распознать секрет, скрытый в произвольной строке. Хеш также не является
обезличиванием: для чувствительного низкоэнтропийного входа нужна отдельная
политика хранения. Удалённому поставщику передаются данные только при явном
AllowExternal для выбранных цели и класса данных. Класс данных устанавливает
доверенная сторона, а не модель. Приёмщик реальных задач должен проверять его
по реестру репозитория, а не принимать самозаявление клиента.

Для общего реестра предлагаются следующие входы. Это требования к согласованию,
а не принятая общая схема и не частные назначения узлов.

| Внешнее поле | Использование/владелец |
| --- | --- |
| node/runtime ID и версия | Разрешённый экземпляр адаптера; вне model/provider core |
| worker/provider/model ID, версия контракта | Явное назначение, проверка возможностей |
| роли | Внешняя политика переводит роли в конкретные действия; строка роли не даёт права |
| repository/target ID и actions/effect | Точное разрешение цели и действия |
| data class и разрешённые получатели | Политика допустимой передачи данных, включая внешний provider |
| policy ID/version, срок действия, отзыв | Снимок полномочий и правила автономного режима |
| бюджет времени, размера, работы/стоимости | Проверяемые единицы и общий учёт; реальные деньги пока не реализованы |
| task/operation/attempt, lease generation, correlation | Причинная связь и защита от устаревших событий |
| версия входного снимка и evidence/artifact reference | Проверяемость результата; не утверждение исполнителя |

MN-01 должен определить правила устаревших/отозванных полномочий при потере
связи, авторитетного владельца поколения при нескольких узлах и общий учёт
бюджета. Локальные SQLite CAS и сроки R4 не решают распределённое согласование.
До этого R5 получает только согласованный местный контракт; выбор транспорта
и реальные подключения остаются отдельной задачей №12. Runtime R6 (№8)
по-прежнему зависит от R4 и R5. Частная инфраструктура и политики сюда не копируются.
