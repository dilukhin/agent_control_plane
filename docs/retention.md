# Ограниченное хранение R3.3

Очистка является явной операцией обслуживания. Ядро не запускает фоновую службу и не удаляет историю при обычном открытии базы. Политика применяется одинаково к memory и SQLite; SQLite выполняет каждый пакет одной транзакцией.

## Сроки и бюджеты

| Класс | Срок / условие удаления |
| --- | --- |
| Tasks | 30 суток после явного завершения; все операции конечные, активных reservations нет |
| Operations и scopes | Вместе с полной историей операции после истечения срока её конечной задачи |
| Attempts/leases, revocations | В одной транзакции с соответствующей operation |
| Evidence, verifications и связи | В одной транзакции с owner operation, без частичного удаления доказательств |
| Messages/dedup с существующей задачей | Не ранее очистки конечной задачи и истечения собственного семидневного окна повторной доставки |
| Messages без задачи | После семи суток от приёма либо issued_at, если он позднее; только за пределами сохранённого окна приёма |
| Неопределённая/активная работа | По возрасту не удаляется; сначала проверка результата и завершение задачи |
| Migration history, replay floor | Срок жизни базы; обычная очистка их не удаляет |
| Очереди, внешние файлы, отдельные журналы диагностики | Пока не реализованы; данная очистка ими не управляет |

Сроки закреплены константами `TerminalRetention` и `ReplayWindow`. Это версия политики R3.3; её изменение требует проверки совместимости, особенно уже удалённой истории сообщений. API принимает бюджеты одного вызова: 1–100 задач и 1–10 000 удаляемых строк. Рекомендуемое начало — 25 задач / 1000 строк, затем настройка по измерениям. Один update строки replay floor является дополнительной постоянной работой и не включён в счётчик удалений.

SQLite ограничивает время вызова общим transaction budget (по умолчанию 10 секунд) и context вызывающей стороны. Ошибка или отмена откатывает весь пакет. Лимит строк ограничивает удаления, а не все прочитанные индексные записи или размер данных в байтах. Уменьшайте пакет при нехватке времени. Memory остаётся небольшим справочным хранилищем и использует копирование состояния для атомарности.

## Завершение задачи

`FinalizeTask(ctx, taskID, revision, now)` использует CAS и консервативно считает все операции обязательными. Незавершённая операция или reservation запрещает завершение. Все succeeded дают completed; подтверждённый конечный failure — failed; все cancelled — cancelled. Смешанный набор succeeded/cancelled требует отдельной явной политики и здесь не угадывается. Пустая задача автоматически завершённой не считается.

После завершения задачи нельзя добавлять операции, новые evidence или новые messages. Уже принятые сообщения в допустимом окне остаются повторными доставками. Входящие сообщения исполнителя всё равно требуют проверки полномочий в доверенном контроллере. Закрытие задачи не заменяет verification её операций.

## Защита от повторного исполнения после удаления dedup

Приём нового сообщения ограничен семью сутками по `issued_at`; допустимое отклонение часов в будущее — пять минут. Проверка использует часы контроллера. Старое сообщение возвращает `ErrExpiredMessage`, даже если запись dedup ещё хранится. Это явное уточнение внутреннего API R3.1/R3.2; wire protocol остаётся 1.0. Длительная задача может получать новые сообщения с новыми идентификаторами и актуальным временем; её сохранённая identity не истекает вместе со старым сообщением.

Перед очисткой сохраняется монотонная `message_floor` — самая ранняя допустимая секунда issued_at. Её обновление атомарно с удалениями. Возврат часов назад или перезапуск не открывает уже удалённое окно повторной доставки. `expires_at` учитывает время приёма и issued_at, поэтому запоздало принятое сообщение не удаляется преждевременно. Для сообщений v1/v2, где время приёма неизвестно, миграция отсчитывает консервативные семь суток от момента обновления базы.

Границы очистки используют целые UTC-секунды и строгие сравнения: запись на границе остаётся до следующей секунды. Часы контроллера должны быть достоверными; скачок вперёд способен закрыть окно приёма, а понижение сохранённой границы автоматически не выполняется. Устойчивые task/operation/message IDs не переиспользуются. Запрет старых сообщений не является аутентификацией или защитой от подделки нового сообщения — это ответственность доверенной границы R4/R5.

## Вызов и продолжение очистки

```go
result, err := store.Collect(ctx, persistence.GCOptions{
    Now: time.Now().UTC(), After: cursor,
    MaxTasks: 25, MaxRows: 1000,
})
```

При `More=true` следующий вызов использует `Next`, который может быть пустым при частично обработанной первой задаче. Каждый вызов ограничен; вызывающий код также должен ограничить число пакетов за один цикл обслуживания. При `More=false` текущий проход окончен. Следующий периодический проход начинается с пустого cursor, чтобы увидеть добавленные или вновь допустимые задачи с меньшими ID.

Каждая operation удаляется целиком вместе с попытками, отзывами, evidence и verification. Если её история больше оставшегося бюджета, пакет заканчивается и продолжится с этой задачи. Если история больше полного заданного бюджета, операция остаётся целой, а `OversizedOperations`/`DeferredTasks` сообщают о пропуске. Можно увеличить бюджет до 10 000 строк; более крупная история требует отдельного проверяемого решения, а не скрытого снятия ограничения.

История большой конечной задачи может очищаться несколькими пакетами по операциям. Task metadata остаётся до удаления всех операций и сообщений. После начала разрешённой очистки клиент не должен рассчитывать на полную историю этой задачи; ещё существующая operation всегда сохраняет свои доказательства целиком. Foreign keys и транзакция защищают от orphan records. Нет удаления только по возрасту для активной задачи, unknown outcome, reservation или связанных с ними сообщений. Новые сообщения с известной противоречивой привязкой task/operation/attempt отклоняются. Старые ошибочные ссылки на другого существующего владельца сохраняются консервативно, пока такой владелец не удалён.

## Обслуживание файла SQLite

`Repository.Maintain(ctx, pages)` освобождает не более 1–1024 страниц через incremental vacuum, отдельно от выполнения операций и очистки записей. Полный VACUUM не вызывается. Схема проверяется под той же блокировкой записи; context и transaction budget действуют и здесь. Освобождение страниц проверено через фактический `freelist_count`.

WAL checkpoint остаётся стандартным механизмом SQLite. При длительном чтении WAL может временно расти; лимит строк очистки не является жёсткой квотой размера DB/WAL. Безопасность не позволяет удалять нерешённую работу ради экономии места. Нужны наблюдение за диском и прекращение нового приёма на уровне будущего runtime при нехватке ресурсов; системное регулирование нагрузки относится к R7.

## Совместимость и проверка

Схема v3 добавляет `messages.expires_at`, `retention_state` и индексы. SQL v1/v2 неизменен; обновление сохраняет неопределённые операции, reservations и revocations. Старый binary отвергает v3. Проверены полное и частичное по задачам удаление, предельные бюджеты, защищённые записи, свежий dedup, откат всего пакета, откат часов, повторное открытие, цепочка retry/revocation и ограниченное обслуживание страниц. R3.1–R3.3 вместе закрывают #10; следующий этап — R4 (#11).
