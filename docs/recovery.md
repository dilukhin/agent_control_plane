# Восстановление R3.2

Восстановление выполняет доверенный контроллер через `InspectRecovery` и `InvalidateAttempt`; открытие SQLite само по себе не запускает работу и не отзывает чужие полномочия. Это библиотечный механизм без выбранной службы, планировщика или транспорта.

## Порядок

1. Открыть хранилище: миграции, проверка целостности и настроек выполняются до работы ядра.
2. Читать `InspectRecovery(ctx, afterID, limit)` страницами по 1–100 операций. Пустой `Next` завершает обход; полный последний пакет может потребовать дополнительного пустого чтения. Каждая страница — согласованный снимок. При параллельном добавлении записей повторить обход: страницы разных вызовов не являются единым снимком.
3. Сопоставить сохранённые состояния с фактической доступностью исполнителей. `pending`/`ready` не означают автоматический запуск; `verified_completion` и `known_failure` отражают подтверждённое ядром конечное состояние. `evaluate_execution` требует оценки executing/verifying; `unknown_outcome` — проверки фактического результата. В странице также возвращаются состояние задачи, текущая попытка и факт отзыва её полномочий.
4. Если определена потеря достоверности выполнения, вызвать `InvalidateAttempt` с ожидаемой revision, точным attempt ID, причиной и наблюдением. Он атомарно сохраняет наблюдение, отзыв полномочий и unknown_outcome, увеличивает revision и переводит попытку в uncertain. Блокировки ресурсов, ID попытки и поколение сохраняются.
5. Выполнить только чтение фактического состояния целевого объекта. Затем `BeginVerification` и проверка по действующей политике. `ApplyVerification` сохраняет результат вместе с переходом. Только доказанный безопасный повтор допускает ready и новую попытку с новым поколением.

Перед отзывом из-за собственного перезапуска контроллер должен установить принадлежность затронутой работы. Запуск второго процесса не даёт права объявлять все чужие операции потерянными. Причины: `controller_restart`, `lease_expired`, `ownership_lost`. Истечение срока устанавливает доверенная внешняя политика по её метаданным; длительность lease, heartbeat и автоматический таймер не выбираются этим изменением и относятся к R4. Перед применением входящего события контроллер обязан обработать известное ему истечение срока и проверить полномочия.

## Полномочия и безопасность

`CheckActiveAttemptContext` отвергает отозванную или uncertain/closed попытку, даже если все старые идентификаторы совпали. Возврат unknown_outcome → verifying не восстанавливает полномочия старого исполнителя. Методы изменения состояния — интерфейс доверенного контроллера; событие исполнителя необходимо применять в `ProcessMessage`, проверив там же полномочия. Поздний отчёт можно сохранить как evidence без признания его авторитетным результатом.

Отзыв полномочий ядра не останавливает физический процесс и не является защитой внешнего объекта от устаревших записей. Перед retry политика обязана доказать остановку старого исполнения либо безопасность механизма идемпотентности/проверки поколения на целевом объекте. Один `RetryExecutionSafe=true` без этой проверки не является достаточным основанием для доверенного контроллера.

Повтор сообщения с тем же содержимым пропускает обработчик; collision отклоняется. Повтор решения с устаревшей revision требует перечитывания. Нет автоматических повторов изменяющего действия при busy, timeout, restart или истечении полномочий. Наблюдение об отзыве не подменяет verification результата.

## Совместимость и проверки

Схема v2 добавляет таблицу `revocations` со ссылкой на попытку и наблюдение. SQL v1 не меняется. Пустая БД и v1 обновляются последовательно; предыдущий бинарный файл отвергает v2. Данные v1 без revocation продолжают читаться; uncertain-попытки уже не обладают полномочиями. Protocol остаётся 1.0.

Общие тесты memory/SQLite проверяют классификацию, страницы, отзыв, откат, CAS, stale attempt, сохранение reservation и безопасный повтор. Проверка двумя дочерними процессами выполняет конкурирующие запуски над общим ресурсом, аварийный выход без Close, последующее восстановление и повторное открытие. SQLite отдельно проверяет обновление fixture v1 с сохранением данных. Ограничение ожидания блокировок проверяется существующим тестом R3.1.

Восстановление не очищает историю. Ограниченное хранение и обслуживание базы реализованы отдельно в [R3.3](retention.md).
