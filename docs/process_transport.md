# R5: ограниченный местный процессный транспорт

Принятый первый сценарий: [ADR-0003 / Gate C](decisions/0003-first-transport.md), [задача №12](https://github.com/dilukhin/agent_control_plane/issues/12). Реализация: `internal/transport/process`, эталонный процесс: `cmd/acp-reference-worker`, независимая проверка фикстуры: `internal/reference`.

Это первый эталонный путь MVP R1–R5 на Windows/Linux. Процесс ОС и стандартные потоки настоящие; искусственны предметные данные и поставщики. Канал ChatGPT Web к рабочему агенту, удалённая машина, платная модель, установка и R6 этим результатом не реализованы.

## Композиция и владельцы

Доверенный контроллер создаёт Task/Operation, задаёт ExactPolicy и передаёт Worker-адаптер существующему `execution.Runner`. Канонические сообщения, попытки, CAS, дедупликация, verification и recovery остаются в R2–R4. Транспорт не получает отдельной очереди, БД, автоматических повторов или собственной машины состояния задачи.

`process.New(Config{Executable: workerPath}, actor, providerID)` создаёт адаптер. `workerPath` — абсолютный путь к известной собственной сборке `cmd/acp-reference-worker`; на Windows требуется `.exe`. Файл должен быть обычным, не symlink, а на Linux — исполняемым. Целостность доверенной сборки и родительских каталогов обеспечивает композиция; одна проверка имени/Lstat не является защитой от подмены тем же пользователем ОС.

Аргументы бинарного режима — `--acp-worker-v1`, назначенный actor и явно выбранный provider. `Config.FixedArgs` допускает только заранее заданный префикс доверенного запуска (в тестах — режим проверочного executable), копируется при создании и не берётся из Job. Request не может выбирать программу, аргументы оболочки, cwd, env или запасного поставщика. Адаптер не вызывает shell. Сам процесс — доверенный код того же пользователя; это не sandbox для произвольной программы.

Capabilities/Accept — быстрые местные проверки без запуска процесса. Поддержаны только `analyze/read_only`, `synthetic`, `test.echo/echo-v1` и `test.digest/sha256-v1`. Отказ до выдачи попытки не создаёт процесс. Отказ запуска/ёмкости после выданной Attempt консервативно становится unknown через Runner; сам транспорт работу не повторяет.

Дочернему процессу доступны только ограниченный Job и потоки. Store, SQLite-файл и функция verification не передаются. Входная метка synthetic не распознаёт скрытые секреты автоматически: доверенная сторона обязана передавать только искусственные данные этого сценария.

## Кадры версии 1

Каждый кадр — четырёхбайтовая unsigned big-endian длина в байтах и UTF-8 JSON указанной длины. Нулевая длина и размер свыше 1 MiB отклоняются до выделения полного входного буфера. Запрещены неизвестные поля, повторённые и регистровые дубли ключей, лишний JSON, неверный UTF-8 и вложенность свыше 32. Неподдерживаемая версия не мигрирует неявно.

| Поле / вид | Назначение |
|---|---|
| `version: "1"` | Версия частного кадрирования адаптера, отдельно от control protocol 1.0 |
| `binding` | Точные task/operation/attempt/lease/generation/correlation/offer/worker/provider/model |
| `job` | Один ограниченный R4 Job, только в первоначальном кадре |
| `heartbeat` | Сигнал ребёнка; контроллер проверяет действующие права и принадлежность Attempt |
| `continue` | Ответ контроллера, разрешающий продолжить текущую контрольную точку |
| `result` | Один Claim: временный Output и Units; не verdict |
| `error` | Фиксированные `provider_failed/budget_exceeded/unsupported/timeout/cancelled`; исходный текст ошибки не возвращается |
| `pid` | Проверка соответствия известному принадлежащему запуску процессу; не устойчивый ID задачи и не удалённая аутентификация |

Binding каждого ответа сравнивается с выданным Job, а не используется для выбора другой операции или полномочий. В ответе нельзя прислать новый Job. Разрешены только ожидаемые поля соответствующего вида. Корректный результат принимается после чистого EOF и успешного завершения процесса: лишний результат, мусор, обрыв либо ненулевой exit code не превращаются в успех.

Ребёнок выполняет контрольную точку и ждёт `continue` перед вызовом поставщика. Политика и владение проверяются штатным heartbeat Runner. Результат также проходит завершающую проверку R4 и существующий RecordWorkerReport; transport receipt сам не даёт succeeded.

## Ресурсные пределы и очистка

- Пределы R4: до 64 KiB входа/выхода, 65536 тестовых единиц, 5 минут и 32 сигналов активности, включая сигналы контроллера. Политика/запрос могут только уменьшать пределы.
- Идентификатор/ссылка адаптера — до 256 UTF-8 байтов, conflict scopes — до 32. Это ограничения первого адаптера, не изменение общих ID R1.
- На один экземпляр Worker по умолчанию до четырёх активных запусков, настройка 1–32. Независимые операции могут выполняться одновременно; переполнение не создаёт очередь или скрытый retry. Глобальный бюджет всех экземпляров остаётся у композиции.
- Родитель читает stdout одновременно с ожиданием процесса. stderr дренируется без хранения текста; после 4096 байтов вызов отменяется с фиксированным ограничением. Заполненная труба не должна удерживать контроллер бесконечно.
- Ожидания связаны с контекстом и Deadline. `CommandContext` останавливает только принадлежащий запуску handle; `WaitDelay` и завершающее ожидание ограничены двумя секундами. Нет поиска/остановки по имени или чужому PID.
- Слот удерживается до окончания Wait и обработки потоков. Если подтверждение очистки не получено в срок, возвращается ErrCleanup, а слот освобождается только после фактического завершения; повторные отказы не наращивают число брошенных обработчиков без предела.
- Эталонный ребёнок не создаёт своих процессов. Принудительная очистка произвольного дерева процессов и изоляция вредоносного кода не обещаются.

`Snapshot` хранит только ограниченную текущую диагностику: число стартов, завершённых Wait, heartbeat, активность и последний PID. Она не сохраняется в Git/SQLite, не содержит пути/argv/вход/выход и не заменяет evidence результата. `WaitIdle(ctx)` — местный барьер очистки, когда доверенная сторона прекратила новые подачи; он не выдаёт разрешение на повтор. Рутинного внешнего сбора данных нет.

## Окружение и данные

Дочернему процессу не наследуются PATH, HOME, credentials, proxy/provider-настройки или всё окружение родителя. Создаётся явно непустой объект списка (в том числе список нулевой длины): `nil` в Cmd.Env означал бы полное наследование. Передаются только существующие SYSTEMROOT/WINDIR/TEMP/TMP, нужные среде Windows/временным файлам. Значения не попадают в обычные логи.

Ни stderr, ни вход/выход, ни текст ошибки декодирования не сохраняются как обычное evidence. Контроллер получает Output временно через существующий Outcome R4. Хеш не является обезличиванием низкоэнтропийных частных данных; реальные данные и долговременные артефакты требуют отдельного доменного договора. Файлового хранилища результатов здесь нет.

## Независимая verification

Эталонная политика `internal/reference.Verify` применима только к зарегистрированной фикстуре `fixture/r5-v1`, точной искусственной строке Input этого пакета, analyze/read_only и `reference-check/v1`.

Контроллер сравнивает фактически полученный Output с ожидаемой строкой либо самостоятельно вычисленным SHA-256. Дополнительно сверяются digest/Units, операция, Attempt/Lease/Generation и политика. Actor проверяющего отличается от владельца попытки. Заявление ребёнка, его PID, успешный exit или digest без Output не являются достаточной проверкой.

Собственное target observation проверяющего и VerdictSatisfied записываются атомарно через существующий `ProcessMessage`; стабильный ID делает повтор проверки идемпотентным. Неверный ответ остаётся verifying и не становится succeeded. Это отдельная фиксированная reference policy, а не универсальный verifier пользовательских задач.

После проверки всех операций контроллер явно вызывает существующий `FinalizeTask`. Заявление ребёнка не закрывает задачу; в полном E2E проверены отказ преждевременного завершения и сохранение TaskCompleted после повторного открытия SQLite.

## Unknown и восстановление

Разрыв, отмена, timeout, неподдерживаемый ответ, падение, превышение лимита и потеря certainty после принятия дают unknown_outcome/отзыв через Runner/R3. Проверяется фактическое состояние, сохраняются IDs и evidence; нет скрытого второго вызова.

После reopen SQLite `InspectRecovery` только классифицирует запись. Повтор Execute уже принятого предложения подтверждает дедупликацию; после истечения его срока возможен ранний отказ до dedup. Такой отказ не доказывает failure и не разрешает запуск с новыми ID.

В эталонном сценарии разрешённый retry требует отдельной проверки: старый принадлежащий процесс завершён, цель действительно неизменяемая synthetic/read_only, предыдущий результат не подтверждён. Verifier переводит unknown → verifying и записывает retry-safe verdict; только затем выдаются новая Attempt/Lease/MessageID и RetryOf. Этот вывод нельзя переносить на внешнюю mutation или неизвестный удалённый процесс.

## Совместимость и проверки

Control protocol остаётся 1.0, SQLite — v3. Нет новых таблиц, миграций, зависимостей или обязательных полей прежних записей. Кадрирование 1 поддерживается только этим новым адаптером, другие версии дают явный отказ. Установка и сетевой транспорт не изменяются.

Проверки `internal/transport/process` собирают настоящее `cmd/acp-reference-worker` в собственном временном каталоге и запускают его по абсолютному пути. Проверяются разные PID, оба поставщика, независимый verifier, SQLite reopen, неизвестный исход и явный retry, дубликаты, восемь конкурирующих предложений, параллельные операции, ёмкость, ложный валидный Claim, malformed/foreign frames, EOF/exit, некооперативный ребёнок, stderr и отсутствие унаследованной тестовой credentials-переменной. Под race дополнительно вызывается настоящий Serve в инструментированном дочернем тестовом процессе. Отмена незавершённого Serve-input проверяется отдельно.

Локальная cross-build не заменяет native Windows tests. Точные команды, версии и фактические CI фиксируются в [датированном отчёте R5](validation/R5_process_transport_2026-11-01.md).
