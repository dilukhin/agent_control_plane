# Первый полезный запуск: конечная местная проверка проекта

Пользователь 2 ноября 2026 года поручил сохранить понятное объяснение системы и продолжить до возможности практической пробы на незавершённом проекте, например LanFabric или Struna. Для первого результата выбран существующий местный проверочный сценарий LanFabric. Устройство для визуальной проверки Struna здесь недоступно.

Это прикладная композиция R2–R5, которая не требует знаний ScopedKB. Порядок и prerequisites runtime R6 не меняются. Новые язык, зависимость, БД, сетевой протокол, scheduler и права не вводятся.

## Принятое решение

Добавить `cmd/acp` и `internal/localcheck`: один явно выбранный оператором executable, фиксированные аргументы из местного профиля, точный список входных файлов, конечные время и вывод. Такой профиль является доверенной конфигурацией композиции. Он не берётся из Job, ответа модели или наблюдения.

Обычная проверочная программа не говорит на wire-протоколе эталонного worker R5. Поэтому отдельный `execution.Worker` адаптирует непосредственный дочерний процесс к существующему Runner. Протокол R5 и его эталонный бинарный файл не расширяются произвольным shell-входом. Программа запускается напрямую, без добавляемой оболочки.

Команда `prepare` создаёт новый местный профиль для точных исходников либо их проверенного CRLF/LF-эквивалента. Она не запускает программу, не меняет проект и не принимает произвольное изменение исходников под видом смены строк. Подготовленный профиль затем закрепляет фактические байты выбранной копии.

Проверки могут создавать временные файлы и `__pycache__`. Их operation консервативно имеет `effect_class=mutation`, `idempotency_mode=unknown` и reservation по каноническому каталогу workspace. Координация действует внутри одной БД состояния ACP; разные каталоги состояния не образуют общую блокировку. Входной снимок содержит контрольные суммы выбранных файлов, а не обещание неизменности всего диска.

## Predicate результата и проверка

Успех означает: выбранный непосредственный процесс наблюдался завершившимся с кодом 0, пределы соблюдены, выбранные исходные байты после него совпали с исходным снимком. Это подтверждает конечную проверку, а не исправность всего проекта или работу VPN на VPS.

Worker возвращает только связанную с попыткой квитанцию. Контроллер сравнивает её с наблюдённым процессом и временным выводом, сохраняет отдельный файл, перечитывает его и сопоставляет digest с сохранённым worker_report/намерением. Независимый от дочерней программы controller actor применяет verification и FinalizeTask. Ненулевой обычный exit и изменение выбранного файла дают известный неудовлетворительный результат. Отмена, потеря выполнения, превышение вывода и неподтверждённый COMMIT не разрешают повтор.

Все задачи используют R3 SQLite v3, CAS, попытки, evidence и reservations. Raw argv, workspace paths и stdout/stderr не записываются в БД или квитанции. Вход/выход и профиль должны быть свободны от секретов; хеш не является анонимизацией. Вывод доступен только по явному местному `--show-output`, хранится в памяти не более 64 KiB и не отправляется внешнему получателю.

## Восстановление и хранение

Повтор существующего task ID не запускает программу. `recover` может завершить проверку уже reported-операции с точной сохранённой квитанцией, без вызова executable. Нет квитанции или нарушена связь — нет подтверждения. Для executing/unknown после потери контроллера требуется отдельное установление фактического состояния; универсального автоматического снятия блокировки здесь нет.

Состояние размещается в отдельном каталоге с явным маркером владельца; чужой непустой каталог не принимается. На Windows оператор обеспечивает приватные ACL, поскольку POSIX mode не заменяет Windows ACL. Результаты подчиняются R3: конечная история 30 суток, незавершённая работа защищена. `gc` делает ограниченный пакет и возвращает курсор; удаление одной старой квитанции требует её явного ID и отсутствия владельца Task. ID после очистки не переиспользуются; глобальная однократность через произвольное переименование задания не обещается.

## Граница доверия и дальнейшая работа

Это доверенная программа того же пользователя ОС. Она потенциально может изменить файлы, использовать сеть и породить другие процессы; список inputs и снятие переменных окружения не являются песочницей. Контроллер наблюдает/останавливает только непосредственный процесс. Профиль LanFabric предназначен для существующих temp/mock local checks, без живых серверных команд. Подключение произвольного агента, shell, privileged actions или deployment потребует собственного ограниченного задания и проверки.

Местный запуск не реализует R6, knowledge ingest, фоновые задания, платные модели или связь ChatGPT Web с установленным агентом. Он даёт проверяемый прикладной путь, пригодный для первой пробы уже сейчас. Управляемая установка в agent-toolchain остаётся отдельной задачей владельца.

## Уточнение после пробы Windows 2 ноября 2026 года

В local.command на Windows явно сохраняется USERPROFILE родительского процесса, чтобы стандартное определение домашнего каталога работало. Полное окружение и переменные с учётными данными не наследуются; на Linux список не расширяется. Это доверенная программа того же пользователя ОС, а не песочница. Схема состояния и профиля не меняется, старые задания не перезапускаются. [Отчёт о пяти ошибках и сравнительном воспроизведении](../validation/windows_local_check_pilot_2026-11-02.md) отделяет исходный отказ LanFabric от корректной обработки результата ACP. Исправление проверяется новым осмысленным заданием; старый failed сохраняется.
