# Фиксация обсуждения качества агентной работы — 1 ноября 2026 года

Тип: датированный протокол происхождения решений и границ публикации. Не нормативная копия программы и не свидетельство runtime-приёмки.

Канонический обзор предлагаемой редакции: [программа](../agent_experience_improvement_program_ru.md). Координация: [#8](https://github.com/dilukhin/agent_control_plane/issues/8).

## 1. Запрос пользователя и разрешённый результат

Обсуждение началось с вопроса, что даст выпуск YC G1–G4. Пользователь отдельно указал на частые окна разрешений обычной работы OpenCode, которых сама модель может не видеть, и механическое использование Allow always. Затем сопоставил это с существующей программой накопления опыта применения утилит, предложил GitHub-базу и периодический разбор в Web с разной срочностью.

После рассмотрения вариантов пользователь согласовал размещение документов и связей задач по проектам и попросил handoff для продолжения в agent_control_plane. Разрешён текущий документационный пакет через ветки/PR и обновление навигации существующих задач. Это не разрешение на автоматический сбор, создание общей базы, расписание, изменение пользовательской policy, слияние всех PR или развёртывание.

Итоговая структура: один общий документ, существующая #8 как вход координации, отдельные собственные методики ScopedKB и opencode_permissions, краткие дополнения задач agent-safe/agent-toolchain. Новая дублирующая программа/репозиторий для хранения только плана не создаётся.

## 2. Реестр обсуждения и принятые границы

| ID программы | Источник вывода / что сохраняется |
|---|---|
| D01–D02 | Пользовательский приоритет — обычная работа без бессмысленных остановок. Узкий YC-выпуск сам по себе этого не решает. |
| D03–D04 | Действующая safety-модель сохраняется. Native-first и узкие проверяемые операции вместо blanket shell allow; JSON validator — только пример кандидата. |
| D05–D06 | Permission events, вопросы модели, guard и реальные окна раздельны. Учитываются effective policy, always и условия сравнения. |
| D07–D09 | Объединение программы, не компонентов. GitHub хранит очищенные материалы; знания и выпуск кода имеют разные состояния. |
| D10–D12 | Нужен знаменатель успешных операций, наблюдаемый источник, очистка и защита от инструкций внутри данных. |
| D13–D14 | S0–S3 отдельно от полномочий. Немедленная safety-остановка не ждёт GitHub/Web; unknown не разрешает повтор. |
| D15–D17 | W0–W3, ограниченные пакеты, дедупликация, защита от рекурсии; scheduled runtime требует фактической проверки. |
| D18–D20 | Принятые рекомендации возвращаются агенту; аудитор/профили моделей не блокируют ранний цикл; нужен один доказанный практический результат. |

Полные смысловые положения D01–D20 находятся в единственном общем документе. Кандидаты параметров отдельно от обязательных границ: ежедневный/еженедельный режим, пять групп, один PR, двукратное сокращение остановок. Они не объявляются установленным нормативом или результатом.

## 3. Исправления возможных неверных трактовок диалога

1. Раннее объяснение состояния G3/G4 было пересказом, не исходной приёмкой. Этот пакет не принимает эти этапы; в следующем диалоге нужен фактический отчёт/решение владельца, если этап влияет на запуск.
2. Снимок запроса Python не доказывает безопасность всего интерпретатора, точный effective rule или lifetime always установленной версии. Снимок и машинные пути не публикуются.
3. Событие asking не приравнивается к увиденному окну. Самоотчёт модели не заменяет наблюдение UI; неизвестная величина не нулевая.
4. Частые нажатия Allow always не обучают автоматическую политику безопасности.
5. Согласие сохранить план не выдаёт постоянных прав будущему обработчику и не создаёт расписания.
6. Общая база имеет конкретное обоснование, но имя, видимость, права и отдельное создание ещё должны быть приняты. Прежнее «не создавать общий репозиторий» не снято скрыто.
7. Ранний ручной разбор не обходит prerequisites R3–R5 и не выдаётся за готовый ScopedKB v2 или R6.
8. W1 уточнён до оформления задач и результатов; изменение исполняемого кода/активной инструкции относится не к W1. Тип файла Markdown не является доказательством низкого риска.
9. Изменение документов не закрывает #15/#25/#39/#48/#60/#61, не возобновляет общий RemoteProcessSpec и не превращает #34 в сборщик телеметрии.
10. Исправление доставляется действующей update-policy; новый обязательный ручной pin каждого штатного обновления не вводится.

## 6. Проверка для публикации

Через GitHub Connector перечитаны runtime bundle, AGENTS, README, baseline и план agent_control_plane. Исходная основная ветка: commit `c149301a82f0980787dea092cb8ccf0f08412dc0`, tree `804e983ff0648c80012fa0bc7997bc3d5e4ebb4c`. В ней R3 завершён; R4 предложен отдельно в PR #19, который при проверке открыт и не слит, head `b48c1d6bc5792b1d4b1ccf7843c266a405e0ddf4`. Это контекст продолжения, не новая приёмка R4.

Документационный пакет не запускает Go/Windows/OpenCode/cloud проверки локально и не заявляет их PASS. Состояние CI документационного PR фиксируется в PR и handoff после публикации. Не используются git/gh как удалённый транспорт, не меняются прежние ветки R4 и пользовательские машины.

Перед слиянием: сверить только ожидаемые Markdown-файлы, актуальный head, ссылки, сохранение истории и границ, затем требуемый проектом CI. При конфликте сначала read-only diagnosis; force/reset/clean запрещены.

## 7. Следующая точка продолжения

Продолжить в проекте `agent_control_plane`, не в отдельном новом репозитории. Сначала принять документационные PR и проверить их связи. Параллельно не потерять уже открытые R4 review-изменения; далее двигаться по #11 -> #12 -> runtime #8. Не перепрыгивать к R6.

Для практической ветки качества после отдельной проверки нужного gate: решить вопрос базы и выполнить один ограниченный ручной цикл на реальных очищенных наблюдениях. Scheduled W0, машинный ingest и автономные W1/W2 имеют отдельные допуски. Стартовый prompt и handoff фиксируют фактические PR/HEAD/CI на момент завершения публикации, а не повторяют старые статусы.
