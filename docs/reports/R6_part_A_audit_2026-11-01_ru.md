## Что уточнено по коду

1. Task/Operation/Attempt/Evidence, CAS, message dedup, recovery и retention уже существуют. ReviewBatch нужно отобразить на них, не строить другое ядро.
2. В protocol/state/persistence нет реализованного хранилища Issue/Escalation. Состояния blocked/awaiting_decision в enum не заменяют API переходов и сохранённую доставку решений.
3. Task не содержит снимок входа, а `Outcome.Output` временный. Message digest не является устойчивым артефактом результата. Восстановление R6 требует отдельного связывания разрешённых байтов и identity.
4. `FinalizeTask` консервативно считает все операции обязательными. Неопределённая запись результата не позволяет закрыть пакет по одному успешному анализу.
5. Транзакционный callback запрещает внешние побочные эффекты. Запись в ScopedKB требует сохранённого намерения, стабильного ключа и actual-state read-back; общей транзакции двух хранилищ нет.
6. Р4 ограничивает длительность/байты/units одной попытки. Денежный и накопительный бюджет через попытки/перезапуск не реализован. В R5 есть лишь детерминированные тестовые поставщики и проверка фиксированной фикстуры.
7. Семантика publication receipt ScopedKB не разрешает хранить выпуск исправления как публикацию знания. Proposal review-status и code release evidence сохраняют разных владельцев.

## Точка продолжения и ограничения

Следующий межпроектный результат — согласованный и проверенный стык со ScopedKB #15. Schema-only реализация v2 необходима по действующему плану, но сама не обеспечивает context/result.
