# Практическая проба ACP на LanFabric

Это конечный местный запуск существующей программы проверки проекта с сохраняемым состоянием. Сначала прочитайте [объяснение системы](how_it_works_ru.md). [ADR-0004](decisions/0004-local-project-check-pilot.md) фиксирует выбранный результат и границы доверия.

## Что понадобится

Бинарный файл `acp` для Linux amd64 либо `acp.exe` для Windows amd64; Python 3.10+ для LanFabric; выбранная локальная копия LanFabric и профиль `examples/lanfabric-local-checks.json` из репозитория ACP. Сам ACP не требует Python для своей работы. Для сборки ACP из исходников нужен Go 1.27.1:

```text
go build -o acp ./cmd/acp
```

На Windows имя выходного файла — `acp.exe`. Команда `acp --version` показывает версию пилота и, в подготовленной сборке, исходный commit. Это отдельный пробный executable; управляемая установка в toolchain пока не реализована.

Профиль LanFabric подготовлен для Python-файлов коммита `cbe7fcb76415133b6eda1902cafde40125a4f77a`, версия 0.0.18. В нём 22 точные SHA-256 исходных и проверочных файлов; запускается `python -B tests_local/run_local_checks.py`. Время ограничено 180 секундами, общий stdout/stderr — 64 KiB. Выбирайте копию проекта, в которой допустимы создаваемые локальными тестами временные файлы и `__pycache__`; серверы и облако не являются целью.

Не переключайте и не очищайте грязную рабочую копию ради примера. Сначала обычным способом установите её точное состояние. При несовпадении байтов ACP откажет до исполнения. Совпадение имени ветки или версии не подменяет проверку файлов. Для изменённой версии нужен отдельно рассмотренный профиль с актуальными суммами, а не отключение проверки. Штатный prepare может создать новый профиль только при доказанном отличии CRLF/LF либо точном совпадении; код проекта он не меняет, существующий выходной файл не перезаписывает.

## Windows

Ниже пример для документированного workspace LanFabricRoot. Уточните фактическое расположение `acp.exe` и исходников ACP. Каталог состояния должен быть новым либо уже принадлежащим ACP. Он находится вне рабочей копии LanFabric.

```powershell
.\acp.exe prepare --spec C:\path\to\agent_control_plane\examples\lanfabric-local-checks.json --program python --workspace C:\Users\Dima\Projects\LanFabricRoot\LanFabric --out .\lanfabric-check-local.json
.\acp.exe check --state C:\Users\Dima\Projects\LanFabricRoot\reports\acp-local-state --task LF-20261102-ACP-01 --spec .\lanfabric-check-local.json --program python --workspace C:\Users\Dima\Projects\LanFabricRoot\LanFabric --show-output
```

`--program` можно задать абсолютным путём к нужному `python.exe`. Если папка содержит пробелы, заключите значение аргумента в кавычки. Для первого прогона желательно выбрать отдельную проверочную копию проекта с известным снимком.

## Linux

```bash
./acp prepare --spec examples/lanfabric-local-checks.json --program python3 --workspace /absolute/path/to/LanFabric --out ../lanfabric-check-local.json
./acp check --state ../acp-local-state --task LF-20261102-ACP-01 --spec ../lanfabric-check-local.json --program python3 --workspace /absolute/path/to/LanFabric --show-output
```

Новый ID означает новое намерение запуска. Сохраняйте его для дальнейших обращений к этой задаче и не переиспользуйте после очистки истории. Повтор той же команды с тем же ID не запускает проверку ещё раз.

## Как читать результат

Основной stdout содержит JSON. Успех выглядит так:

```json
{"task":"LF-20261102-ACP-01","task_state":"completed","operation_state":"succeeded","exit_code":0,"output_bytes":41831,"output_sha256":"...","inputs_match":true}
```

Размер и хеш зависят от среды и времени тестов; они не являются постоянным ожидаемым ответом. Код завершения самого ACP: 0 — выбранная проверка подтверждена; 1 — завершилась с неудовлетворительным результатом; 2 — результат не подтверждён, аргументы/предпосылки неверны либо задание уже существует.

`--show-output` явно направляет временный вывод программы в stderr. По умолчанию raw output не выводится и не сохраняется. Секреты не должны попадать даже в выбранные программы, профили и выходные данные. Не публикуйте весь терминальный журнал автоматически.

Чтобы прочитать сохранённое состояние, закройте программу и выполните:

```text
acp status --state <тот же каталог> --task LF-20261102-ACP-01
```

Эта команда не запускает Python. После известного ненулевого exit вы увидите `failed`; это отличается от `unknown_outcome`. Состояние `executing`, оставшееся после исчезновения контроллера, тоже требует проверки: оно не доказывает, что процесс сейчас жив.

## Если выполнение прервалось

```text
acp recover --state <тот же каталог> --task LF-20261102-ACP-01
```

`recover` умеет только перечитать совпадающую квитанцию уже полученного результата и завершить его verification/Task. Он не выполняет команду и не снимает неизвестный исход. Если выполнение было потеряно до получения достаточных доказательств, нужен отдельный разбор фактического состояния. Не обходите reservation другим ID, другим каталогом ACP или правкой SQLite ради повтора.

Испорченная/исчезнувшая квитанция не заменяется сохранённым хешем. Если программа превысила срок/вывод или могла оставить дочерние процессы, нельзя автоматически считать все её эффекты прекращёнными. Пробный путь предназначен для доверенных конечных местных проверок, а не произвольного shell или установки на сервер.

## Очистка истории

```text
acp gc --state <каталог>
```

Команда использует R3 и ограничивается 25 задачами / 1000 строками за вызов. Если `state.More=true`, следующий конечный вызов получает `--after <state.Next>`. Число вызовов за один сеанс ограничивайте; новый проход начинается без `--after`. Активные и неизвестные операции не удаляются по возрасту.

Одна квитанция может быть удалена отдельно только после 30 суток и удаления её Task:

```text
acp gc --state <каталог> --receipt LF-20261102-ACP-01
```

Не удаляйте state вручную для обхода блокировки. Разные каталоги ACP не координируют общий workspace. Это явная первая утилита, без фонового планировщика и автоматического обслуживания диска.

## Что проверено в первом опыте

На Linux с Python 3.12.14 точные 22 Python blob LanFabric получены через GitHub Connector и совпали с исходным коммитом. Через скомпилированный ACP прошли 252 теста без failures/errors/skips, а также проверки синтаксиса, версии и справки. Состояние прочитано новым процессом, повтор того же ID отвергнут. Выбранные исходные файлы остались прежними. Это local checks, не испытание VPN на VPS.

Сам ACP проверяется отдельно на синтетических процессах: успех, известный отказ, изменение входа, timeout/oversized output, повтор и конкуренция, пропажа/подмена квитанции, восстановление после reported, чужой state и ограниченная очистка. Native Windows/Linux evidence относится к фактическому CI опубликованного коммита; Linux cross-build не заменяет проверку Windows. Точные результаты — в [отчёте пилота](validation/local_check_pilot_2026-11-02.md).

## Уточнение после пробы Windows 2 ноября 2026 года

В local.command на Windows явно сохраняется USERPROFILE родительского процесса, чтобы стандартное определение домашнего каталога работало. Полное окружение и переменные с учётными данными не наследуются; на Linux список не расширяется. Это доверенная программа того же пользователя ОС, а не песочница. Схема состояния и профиля не меняется, старые задания не перезапускаются. [Отчёт о пяти ошибках и сравнительном воспроизведении](validation/windows_local_check_pilot_2026-11-02.md) отделяет исходный отказ LanFabric от корректной обработки результата ACP. Исправление проверяется новым осмысленным заданием; старый failed сохраняется.

Для проверки нового идентификатора используйте `status` с тем же каталогом состояния. Ответ `task_not_found` в stderr и код 2 означают, что хранилище прочитано и задача с этим ID не найдена. Сам по себе код 2 недостаточен. При запуске `check` проверка существования и регистрация ID выполняются заново, в том числе при конкурентном обращении.
